# 任务续行：守住目标、边界和停止条件

这些规则只约束当前用户任务，不新增操作授权；用户最新的明确要求优先。

## 每次续行先对齐

- 记住当前目标、用户约束、已完成项、下一项和完成判据；长任务在工作区保留简短进度，避免重复已完成步骤。
- 追问、状态询问和纠正通常是在调整当前任务。先简短回应，再续行；用户明确取消、暂停或替换任务时按新要求处理。
- 下一次工具调用必须推进未完成项或消除当前阻塞；不要因新线索擅自改成环境探索、安装工具、调试其他应用。

## 入口与失败

- 先确认是 Android 原生界面、DSH WebUI，还是终端。按当前页面/文档判断，仍有实质歧义才问一句。
- WebUI 用实际 CDP 元素；其他 App 用当前读屏/场景。不要猜 `/settings` 路由、Activity 名或 DOM。
- 同一目标连续两次失败：停掉同一方案，读回执和对应文档，换锚点、通道或路线；仍无依据时说明阻塞并询问。不要微调坐标反复赌。
- 缺工具时先确认是否已有等价能力，再按需使用 Termux 包；不要覆盖 App 管理的 node / rg，也不要为普通点击自动提权。

## 完成、交接与中断

- 用户要“点一下/打开供我使用”：按成功派发或交接回执结束该动作，不追加截图、轮询或重放。
- 用户要达到某个状态：动作派发后等界面稳定，用一次目标状态读取判断；`ok:true` 本身不证明目标已实现。
- 成功的 `handoff:true`，或明确终止的 `stop:true` / `next:"none"`：停止该动作链；不要以“验证”为由继续操作用户接手的页面。
  `verify:"none"` 单独出现只表示没有自动验证，不等于任务成功或终止。
- 重启引擎会中断当前会话。确需重启时先告知，使用 `dsh-update restart`；不要自行杀进程或抢占 3080 / 3083。
- 达到用户目标即停止；交付只写已完成、证据与未覆盖范围。不得把隔离测试、派发成功或加载成功写成端到端验收。

## 执行中提醒

App 在进入任务及持续执行时补充[短提醒](references/step-reminder.md)，不是要求你再次复述整份清单。
点击规则见 `a11y-tap-discipline`；证据与实验规则见 `evidence-discipline`。
完整入口与交接说明：`docs DSH-MOBILE`、`$DSH_HOME/AGENTS.md` 的 Hand-off actions。
